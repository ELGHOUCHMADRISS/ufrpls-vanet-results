The `_maps/pls/` directory contains **all static geographic and traffic files** that define the physical simulation environment. Every OMNeT++ configuration in `omnetpp_5pos_full.ini` references files from this directory through its `launchd_*.xml` launch descriptor.

### Naming Convention

```
traffic_{N}veh_{speed-range}_rou.xml    → vehicle routes
simple_{N}veh_{speed-range}.sumo.cfg   → SUMO config

```

Where:

- `{speed-range}` ∈ {`40-60kmh`, `80-120kmh`} — speed regime

## 2. Network Construction Files

These three XML files are the **source inputs** to SUMO's `netconvert` tool. They are not used directly at simulation runtime — the compiled `highway_medium.net.xml` is used instead.

### 2.1 `nodes.nod.xml` — Junction Coordinates

```xml
<nodes>
    <node id="start" x="0"    y="0" type="priority"/>
    <node id="end"   x="1000" y="0" type="priority"/>
</nodes>
```

Defines exactly **two junctions**:
- `start`: at coordinate (0, 0) — west end of highway
- `end`: at coordinate (1000, 0) — east end of highway

Both are `type="priority"` — the lane already on the road has right-of-way (no traffic lights, no yield signs). This is appropriate for a merge/u-turn junction.

### 2.2 `edges.edg.xml` — Road Segment Definitions

```xml
<edges>
    <!-- Chai 2023: 8 lanes, 4 each direction, 1000m, 60 km/h max -->
    <edge id="edge_fwd" from="start" to="end"
          priority="1" numLanes="4" speed="16.67" spreadType="center"/>
    <edge id="edge_bwd" from="end" to="start"
          priority="1" numLanes="4" speed="16.67" spreadType="center"/>
</edges>
```

| Attribute | Value | Interpretation |
|-----------|-------|---------------|
| `edge_fwd` | start → end | Eastbound direction (left to right) |
| `edge_bwd` | end → start | Westbound direction (right to left) |
| `numLanes` | 4 | Four lanes per direction, 8 total |
| `speed` | 16.67 m/s | Speed limit = 60 km/h (Chai Table 2) |
| `spreadType` | center | Lanes are spread symmetrically around the road centre |

### 2.3 `connections.con.xml` — Turn Connections

```xml
<!-- Direct U-turn at end: eastbound → westbound -->
<connection from="edge_fwd" to="edge_bwd" fromLane="0" toLane="0"/>
...
<!-- Direct U-turn at start: westbound → eastbound -->
<connection from="edge_bwd" to="edge_fwd" fromLane="0" toLane="0"/>
```

All 4 eastbound lanes connect to the corresponding 4 westbound lanes at each end, and vice versa. This implements a **U-turn junction**: vehicles heading east turn around at x=1000 and head west, and vice versa. No explicit traffic signal control is needed — the `priority` junction type handles it.

## 3. Compiled Network (`highway_medium.net.xml`)

Generated by SUMO netconvert from the three source files above. This is the file loaded at simulation runtime.

### 3.1 Network Topology

```
     ← ← ← ← ← ← ← edge_bwd (westbound, 4 lanes) ← ← ← ← ← ←
     
 start                                                         end
(x=0, y=0) ————————————————————————————————————— (x=1000, y=0)
     
     → → → → → → → → edge_fwd (eastbound, 4 lanes) → → → → → →
```

**Physical dimensions:**
- Total road length: 1000.04 m (including junction geometry)
- Lane configuration: 4 lanes per direction, lanes indexed 0–3
- Lane lateral offsets (from net.xml shape coordinates):
  - Lane 0: ±11.20m from centre
  - Lane 1: ±8.00m from centre
  - Lane 2: ±4.80m from centre
  - Lane 3: ±1.60m from centre
- Lane width: ≈ 3.2 m

### 3.2 Internal Junction Edges

At each end, SUMO adds internal edges (`:end_0`, `:start_0`) to model the U-turn geometry. These have reduced speed limits (3.65–8.18 m/s) and length 18.69 m, creating realistic deceleration zones at the turnaround points.

### 3.3 Coordinate System

```
convBoundary: "0.00,0.00,1000.00,0.00"
origBoundary: "0.00,0.00,1000.00,0.00"
netOffset: 0.00,0.00
```

The network is axis-aligned with x∈[0,1000]m and y=0 (nominally). The OMNeT++ playground (2000m×500m) is larger than the road to prevent boundary artefacts.

## 4. Radio Configuration (`config.xml`)

This file configures Veins' **radio propagation models** (not to be confused with SUMO configuration). It is referenced by the Veins framework.

```xml
<root>
  <AnalogueModels>
    <AnalogueModel type="SimplePathlossModel">
      <parameter name="alpha"            value="1.8"/>
      <parameter name="carrierFrequency" value="5.890e+9"/>
    </AnalogueModel>

    <AnalogueModel type="TwoRayInterferenceModel">
      <parameter name="DielectricConstant" value="3.0"/>
    </AnalogueModel>
  </AnalogueModels>

  <Decider type="Decider80211p">
    <parameter name="centerFrequency" value="5.890e9"/>
  </Decider>
</root>
```

### 4.1 SimplePathlossModel

| Parameter | Value | Justification |
|-----------|-------|--------------|
| `alpha` | 1.8 | Open highway path-loss exponent (1.6–1.8 range). Lower than free-space (2.0) due to waveguide effect between vehicles. |
| `carrierFrequency` | 5.89 GHz | DSRC/IEEE 802.11p carrier frequency |

Path-loss formula: `PL = (4π·d/λ)^α` with α=1.8.

### 4.2 TwoRayInterferenceModel

| Parameter | Value | Justification |
|-----------|-------|--------------|
| `DielectricConstant` | 3.0 | Dry asphalt road surface (range 3.0–5.0). Models ground reflection. |

The two-ray model adds a ground-reflected component to the direct LOS path. On a flat highway, this creates a distance-dependent interference pattern that reduces effective range at distances above the crossover distance.

### 4.3 Decider80211p

Determines whether a received frame is decodable based on SINR threshold at 5.89 GHz. Works with the physical layer models above to produce realistic packet-level reception.

**Relevance to PLS**: These propagation parameters directly determine the values of `C_ij = log₂(1 + SNR)` computed in the UFRPLS/GPSRCS routing code. The `alpha=1.8` exponent and 5.89 GHz frequency match the values used in the CS formula constants (`UFRPLS_WAVELENGTH=0.05085m`, `UFRPLS_TRANSMIT_POWER=0.01W`).

## 5. Vehicle Route Files (`.rou.xml`)

Ten route files define the vehicle population for each combination of density and speed regime. All share the same structure.

### 5.1 Vehicle Type Definitions

All route files define four vehicle types with identical physical parameters, differentiated only by colour:

| Type ID | Colour | SUMO Hex | Role |
|---------|--------|----------|------|
| `type_legitimate` | Green (0,255,0) | #00FF00 | Relay/intermediate node |
| `type_source` | Blue (0,0,255) | #0000FF | Packet source (vehicle[1]) |
| `type_dest` | Orange (255,165,0) | #FFA500 | Packet sink (vehicle[N-1]) |
| `type_eavesdropper` | Red (255,0,0) | #FF0000 | Eavesdropper (vehicle[0]) |

**Common physical parameters across all types:**

| Attribute | Value | Description |
|-----------|-------|-------------|
| `accel` | 2.6 m/s² | Maximum acceleration |
| `decel` | 4.5 m/s² | Maximum deceleration |
| `sigma` | 0.5 | Driver imperfection (0=perfect, 1=erratic) |
| `length` | 5 m | Vehicle body length |
| `minGap` | 2.5 m | Minimum gap to predecessor |
| `maxSpeed` | 16.67 / 33.33 m/s | Speed limit (slow / fast regime) |

**σ=0.5** creates realistic speed variation: vehicles do not follow the car-ahead perfectly, producing heterogeneous inter-vehicle distances that affect the CS distribution.

### 5.2 Route Definitions

#### Slow-Speed Routes (40–60 km/h)
```xml
<route id="route_east" edges="edge_fwd edge_bwd edge_fwd edge_bwd 
                                edge_fwd edge_bwd edge_fwd edge_bwd"/>  <!-- 8 traversals -->
<route id="route_west" edges="edge_bwd edge_fwd edge_bwd edge_fwd 
                                edge_bwd edge_fwd edge_bwd edge_fwd"/>
```
8 edge segments = 4 full laps (4 × 2 × 1000m = 8000m). At 60 km/h this takes ≈ 480 s, well beyond the 260 s simulation time.

#### Fast-Speed Routes (80–120 km/h)
```xml
<route id="route_east" edges="edge_fwd edge_bwd ... (16 repetitions)"/>
```
16 edge segments = 8 full laps = 16000m. At 120 km/h this takes ≈ 480 s — vehicles never reach the end of their route during the simulation.

### 5.3 Vehicle Placement Design

#### Fixed Positions (depart at t=0)

All vehicles depart at time 0 (`depart="0"`). This avoids the complications of vehicle insertion logic and ensures the network is fully populated from the start.

| Vehicle ID | Role | departPos | Route |
|------------|------|-----------|-------|
| `vehicle00` | Eavesdropper | 900.0 m (default) | route_east |
| `vehicle01` | Source | 50.0 m | route_east |
| `vehicle02..vehicle[N-2]` | Relays | distributed | route_east / route_west |
| `vehicle[N-1]` | Destination | 50.0 m | route_west |

**Key design choice**: Source and destination both start at 50m but on opposite directions. This maximises the multi-hop path length (the packet must traverse nearly the full 1000m highway from east to west or vice versa).

### 5.4 Density-Dependent Spacing

| N vehicles | Relay count | Approx. spacing |
|------------|-------------|----------------|
| 20 | 18 | ~100 m |
| 40 | 38 | ~50 m |
| 60 | 58 | ~33 m |
| 80 | 78 | ~22 m |
| 100 | 98 | ~18 m |

At N=100, the eastbound and westbound relays are placed at ≈18.4m intervals (`(1000-50)/50 ≈ 18.4m` per relay per direction). The 4-lane highway ensures there is no physical collision even at this density.

### 5.5 Eavesdropper Position Gap

In the route files, a deliberate gap exists in relay positions around the eavesdropper's `departPos`:

- **N=20, slow**: Eavesdropper at 900m. Nearest relays: vehicle08 at 850m and vehicle09 in westbound group. Gap ≈ 50m.
- **N=100, slow**: Eavesdropper at 900m. Positions jump from ~890m to ~920m for nearby relays. Gap ≈ 30m.
- **N=100, fast (gen scripts)**: Eavesdropper at 500m. Positions jump from 468m to 528m. Gap ≈ 60m.

This gap ensures no relay vehicle overlaps with the eavesdropper, preventing SUMO collision detection failures.

### 5.6 Departure Speed Design

Departure speeds are staggered (e.g., 11.11, 12.0, 12.5, ..., 16.67 m/s for slow) to:
1. Avoid synchronised acceleration that would produce unrealistic platoons
2. Create immediate speed variation matching the target σ=0.5 distribution
3. Prevent rear-end collisions in the first few seconds of simulation

**Boundary safety**: Vehicles near position 900–970m have capped departure speeds (≤25 m/s at 880m, ≤22.22 m/s at 915m) to prevent them from overrunning the 1000m junction before SUMO's collision detection activates.

### 5.7 Speed Regime Comparison

| Metric | Slow (40–60 km/h) | Fast (80–120 km/h) |
|--------|-------------------|---------------------|
| `maxSpeed` | 16.67 m/s (60 km/h) | 33.33 m/s (120 km/h) |
| Departure speeds | 11.11–16.67 m/s | 22.22–33.33 m/s |
| Route laps | 8 edges (4 laps) | 16 edges (8 laps) |
| Relative mobility | Low | High |
| Beacon staleness | Low | Higher |
| CS variability | Lower | Higher |

## 7. Veins Launch Descriptor Files (`launchd_*.xml`)

Ten launch descriptor files, one per (N, speed) scenario. These are used by `VeinsInetManager` (the SUMO↔OMNeT++ bridge) to start SUMO correctly.

Example: `launchd_20veh_40-60kmh.xml`:
```xml
<launch>
  <copy file="C:\...\highway_medium.net.xml"/>
  <copy file="C:\...\traffic_20veh_40-60kmh_rou.xml"/>
  <copy file="C:\...\simple_20veh_40-60kmh.sumo.cfg" type="config"/>
</launch>
```

### How Launch Files Work

1. VeinsInetManager reads the `launchConfig` XML attribute from the `*.ini` file.
2. `sumo-launchd.py` receives the launch file and:
   - **Copies** all referenced files to a temporary working directory
   - **Starts** SUMO with the `type="config"` file as the main argument
   - **Opens** the TraCI port (9999) for OMNeT++ to connect
3. VeinsInetManager connects to port 9999 and sends TraCI commands.

The `type="config"` attribute marks the `.sumo.cfg` file as the SUMO entry point. The other `<copy>` entries ensure the referenced `.net.xml` and `.rou.xml` files are available in the temporary directory.

## 8. Route Generator Scripts (`.py`)

### 8.1 `analyze_all.py`

**Purpose:** Inspection utility that analyzes all `traffic_*_rou.xml` files in the current directory and prints a diagnostic report.

**What it checks:**
- Total vehicle count and sigma/maxSpeed values
- Eavesdropper gap: positions of nearest relays before and after `vehicle00`
- Average and maximum inter-vehicle spacing among relays
- Maximum departure position
- **Braking safety**: for each vehicle, checks if `pos + v²/(2×4.5) > 1000m`. If so, the vehicle cannot stop before the junction — a SUMO collision risk.

**Output:** Console text only. Not used in the simulation pipeline.

### 8.2 `gen_80veh_fast_fix.py`

**Purpose:** Regenerates `traffic_80veh_80-120kmh_rou.xml` with a specific eavesdropper gap design.

**Design choices:**
- Eavesdropper at position 500.0m (midpoint)
- Gap: 470m → 510m (~30m clear zone around eavesdropper)
- Eastbound: 17 vehicles before gap (pos 113–470m) + 21 after (510–935m) = 38 relays
- Westbound: 17 before + 22 after = 39 relays
- Speed caps at boundary: positions ≥915m use 22.22 m/s, ≥880m use ≤25 m/s
- Lane cycling: `lane = i % 4`

### 8.3 `gen_80veh_reduced_gap.py`

**Purpose:** Alternative variant of `gen_80veh_fast_fix.py`. Produces the same output file but with slightly different speed pool generation logic. The two scripts represent iteration on the route design; `gen_80veh_fast_fix.py` is the cleaner version. Both output to the same `traffic_80veh_80-120kmh_rou.xml`.

## 10. PLS Context Relevance

### 10.1 Why a 1000m Linear Highway?

The single-corridor topology was chosen to replicate Chai et al.'s idealized PLS scenario:

1. **Predictable LOS geometry**: On a straight highway, the distance `d_ij` between any two vehicles is deterministic given their positions. This makes the secrecy capacity formula `CS_ij = max(C_ij − C_ie, 0)` geometrically interpretable — there are no corner effects, occlusions, or building scattering.

2. **Guaranteed multi-hop path**: Source at x=50m and destination at x=50m on the opposite direction means every packet must traverse ≈900–950m of highway, requiring 5–12 hops at 200m communication range. This provides rich statistics on per-hop CS.

3. **Controlled eavesdropper placement**: The eavesdropper's `departPos` is the sole spatial variable in the experiment. By scanning it from 100m to 900m (in 200m-spaced steps), the research characterises how eavesdropper position affects the secrecy capacity envelope along the full route.

### 10.2 Four-Lane Configuration and PLS

The 4-lane design creates **lateral distance diversity** relevant to PLS:

- A relay at position x=500m in lane 3 (nearest to centre, offset ±1.60m) is closer to the eavesdropper than a relay in lane 0 (offset ±11.20m) at the same longitudinal position.
- The difference in `d_ie` (distance to eavesdropper) between inner and outer lanes at the same x position ranges from 3.2m to 9.6m.
- This introduces a few-percent variation in `C_ie`, and therefore in `CS_ij`, across lanes — captured in the `stddev` of the `secrecyCapacity` statistic.

### 10.3 Eavesdropper Gap and Worst-Case CS

The deliberate **relay-free zone** around `vehicle00` (typically 30–50m) has a critical PLS effect:

```
Without gap:
  relay at 895m → eavesdropper at 900m → relay at 905m
  d_ie(895m) = 5m → C_ie very high → CS ≈ 0 for both neighbours
  
With gap:
  relay at 850m → [empty] → eavesdropper at 900m → relay at 950m
  d_ie(850m) = 50m → C_ie moderate → CS > 0 possible
```

Without the gap, any relay within 5–10m of the eavesdropper would have CS≈0 and UFRPLS would have to wait (or eventually drop), artificially degrading both protocols equally. The gap ensures that the eavesdropper experiences realistic "far-field" CS values from its neighbouring relays.

### 10.4 Eavesdropper Position Scanning (PLS Experiment Design)

The Python runner (`run_all_simulations_9.py`) varies the eavesdropper's `departPos` by patching the route XML before each run:

| Position Tag | departPos | Scenario |
|-------------|-----------|----------|
| `e100` | 100m | Near source end — primarily affects short-path CS |
| `e300` | 300m | 30% along highway |
| `e500` | 500m | Midpoint — worst-case for multi-hop CS (affects most relay segments) |
| `e700` | 700m | 70% along highway |
| `e900` | 900m | Near destination end — affects last-hop CS most |

Averaging over these 5 positions gives the **expected CS** independent of eavesdropper location — matching Chai et al.'s Monte Carlo averaging approach.

### 10.5 U-Turn Topology and CS Stationarity

The U-turn design keeps vehicles in circulation for the full 260-second simulation. This creates a **quasi-stationary** topology after the initial transient:

- After ~20–30 seconds, vehicles are distributed along the highway in a pseudo-random pattern driven by σ=0.5 driver imperfection.
- The inter-vehicle distances no longer match the initial uniform spacing.
- CS measurements from t=10s to t=260s therefore represent a realistic distribution of geometric configurations, not just the artificial initial placement.

This is essential for obtaining statistically valid CS means: the routing module accumulates CS samples from all 1000 packets (250s × 4 pkt/s), each experiencing a different geometric configuration as vehicles continuously move and reorder.
