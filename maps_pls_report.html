🏗️ 2. Network Construction Files

Three XML source files feed SUMO's netconvert tool to produce highway_medium.net.xml. They are not loaded at simulation runtime.

2.1 nodes.nod.xml — Junction Coordinates

<nodes>
  <node id="start" x="0"    y="0" type="priority"/>
  <node id="end"   x="1000" y="0" type="priority"/>
</nodes>

Exactly two junctions: start (0,0) at the west end and end (1000,0) at the east end. type="priority" means the vehicle already on the road has right-of-way — no traffic signals required.

2.2 edges.edg.xml — Road Segment Definitions

<!-- Chai 2023: 8 lanes, 4 each direction, 1000m, 60 km/h max -->
<edge id="edge_fwd" from="start" to="end"
      numLanes="4" speed="16.67" spreadType="center"/>
<edge id="edge_bwd" from="end"   to="start"
      numLanes="4" speed="16.67" spreadType="center"/>
AttributeValueInterpretation
edge_fwdstart → endEastbound carriageway
edge_bwdend → startWestbound carriageway
numLanes4Four lanes per direction = 8 total (Chai Table 2)
speed16.67 m/sSpeed limit = 60 km/h
spreadTypecenterLanes spread symmetrically around road centreline

2.3 connections.con.xml — U-Turn Connections

All 4 lanes of edge_fwd connect to corresponding lanes of edge_bwd at the end junction, and vice versa at start. This creates bidirectional U-turns — vehicles bounce back and forth along the 1000m corridor indefinitely.

🗺️ 3. Compiled Network (highway_medium.net.xml)

Generated by netconvert and loaded by SUMO at simulation time. Contains full geometric detail including internal U-turn edges at each junction.

Road Length

1000 m total corridor (x=0 to x=1000). Internal junction geometry adds ≈0.04 m.

Lane Configuration

4 lanes per direction = 8 total. Lateral offsets ±1.60m to ±11.20m from centreline (~3.2m per lane).

Junction Type

U-turn junctions at both ends. Internal edges :end_0, :start_0 model realistic deceleration (speed 3.65–8.18 m/s, length 18.69 m).

Coordinate System

Axis-aligned, y=0. OMNeT++ playground (2000m×500m) is larger than road to prevent boundary artefacts.

📡 4. Radio Configuration (config.xml)

This Veins XML file configures the physical-layer propagation stack used by every vehicle's NIC. It is the direct bridge between SUMO geometry and the PLS secrecy capacity formula.

<root>
  <AnalogueModels>
    <!-- Open highway waveguide — alpha=1.8 lower than free-space 2.0 -->
    <AnalogueModel type="SimplePathlossModel">
      <parameter name="alpha"            value="1.8"/>
      <parameter name="carrierFrequency" value="5.890e+9"/>
    </AnalogueModel>
    <!-- Ground reflection — DielectricConstant=3.0 (dry asphalt) -->
    <AnalogueModel type="TwoRayInterferenceModel">
      <parameter name="DielectricConstant" value="3.0"/>
    </AnalogueModel>
  </AnalogueModels>
  <Decider type="Decider80211p">
    <parameter name="centerFrequency" value="5.890e9"/>
  </Decider>
</root>
ModelParameterValuePLS Significance
SimplePathlossModelalpha1.8Lower than free-space (2.0) → slower signal decay → wider interference range for eavesdropper
SimplePathlossModelcarrierFrequency5.89 GHzλ=0.05085m — matches UFRPLS_WAVELENGTH constant in routing code
TwoRayInterferenceModelDielectricConstant3.0Dry asphalt surface — models ground reflection creating SNR dips at specific distances
Decider80211pcenterFrequency5.89 GHzDSRC channel; determines packet-level reception from SNR
ℹ️

PLS connection: These propagation parameters feed directly into the CS formula CSij = max(Cij − Cie, 0) where C = log₂(1 + Pt·(λ/4πd)² / σ²). With Pt=10 mW, λ=0.0509 m, and σ²=−95 dBm, the 200m communication range follows directly from α=1.8.

🚗 5. Vehicle Route Files (.rou.xml)

Ten route files define the vehicle population for each combination of density × speed regime. All share the same four-role structure.

5.1 Vehicle Roles & Types

Eavesdropper vehicle00

type_eavesdropper (red). Passive listener — no routing module. departPos=900m (default). Position is overridden per experiment by the Python runner.

Source vehicle01

type_source (blue). Runs UFRPLS or GPSRCS. Generates UDP packets at 4 pkt/s toward destination. departPos=50m, route_east.

Relay vehicle[2..N-2]

type_legitimate (green). Runs routing protocol — forwards packets, computes CS per hop. Distributed across full highway.

Destination vehicle[N-1]

type_dest (orange). Receives packets, counts PDR. departPos=50m, route_west (opposite direction to source).

⚙️ 6. SUMO Configuration Files (.sumo.cfg)

One file per (N, speed) scenario. References the shared network and the scenario-specific route file.

<configuration>
  <input>
    <net-file    value="highway_medium.net.xml"/>   <!-- shared -->
    <route-files value="traffic_20veh_40-60kmh.rou.xml"/>
  </input>
  <time>
    <begin       value="0"/>
    <end         value="1000"/>   <!-- OMNeT++ stops via TraCI at ~260s -->
    <step-length value="0.1"/>  <!-- 10 Hz mobility updates -->
  </time>
  <remote-port value="62189"/>  <!-- standalone GUI port -->
  <seed        value="0"/>
  <random      value="false"/>
</configuration>

The end=1000 value is a safety maximum — OMNeT++ terminates the SUMO process via TraCI well before this, at the configured simulation end time (~260 s). The Python runner overrides the seed by passing --seed-set as an argument to SUMO.

🚀 7. Veins Launch Descriptor Files

The launchd_*.xml files are read by VeinsInetManager and executed by sumo-launchd.py to start the correct SUMO process for each OMNeT++ configuration.

<launch>
  <copy file="C:\...\highway_medium.net.xml"/>
  <copy file="C:\...\traffic_20veh_40-60kmh_rou.xml"/>
  <copy file="C:\...\simple_20veh_40-60kmh.sumo.cfg" type="config"/>
</launch>
✅

Execution flow: VeinsInetManager reads the launchd file → sumo-launchd.py copies all files to a temp directory → starts SUMO with the type="config" file → opens TraCI port 9999 → OMNeT++ connects and sends mobility commands each 0.1 s step.

🔧 8. Route Generator Scripts

analyze_all.py — Route Inspection Utility

Globs all traffic_*_rou.xml files, parses vehicle positions, speeds, and lane assignments. Reports:

  • Eavesdropper gap boundaries (nearest relays before/after vehicle00)
  • Average and maximum inter-relay spacing
  • Braking safety check: if pos + v²/(2×4.5) > 1000m → UNSAFE (vehicle cannot stop before junction)

Output is console text only. Run from _maps/pls/ after any route file change.

🔐 10. PLS Context Relevance

10.1 Why a 1000m Linear Highway?

✅

Predictable LOS geometry: On a straight highway, distance dij between vehicles is purely a function of longitudinal position. There are no corner effects, occlusions, or building scattering. This makes the secrecy capacity formula CSij = max(Cij − Cie, 0) geometrically interpretable and replicates Chai et al.'s Monte Carlo idealised model.

10.2 Four-Lane Configuration and PLS

The 4-lane design creates lateral distance diversity relevant to CS:

LaneOffset from centrelineEffect on die
Lane 0 (outermost)±11.20 mLargest die → lower Cie → higher CS possible
Lane 1±8.00 m
Lane 2±4.80 m
Lane 3 (innermost)±1.60 mSmallest die → higher Cie → lower CS

This lateral variation is captured in the stddev field of the secrecyCapacity statistic in result .sca files.

10.3 Eavesdropper Position Scanning

The Python runner patches vehicle00's departPos in the route XML before each run:

TagdepartPosPhysical Scenario
e100100 mNear source — impacts early hops most
e300300 m30% along highway
e500500 mMidpoint — worst-case, affects most relay segments
e700700 m70% along highway
e900900 mNear destination — impacts last hop most

Averaging over all 5 positions yields the expected secrecy capacity independent of eavesdropper location — matching Chai et al.'s Monte Carlo averaging.

10.4 U-Turn Topology and CS Stationarity

ℹ️

The U-turn design keeps all vehicles circulating for the full 260-second simulation. After the initial ~20–30 s transient, σ=0.5 driver imperfection disperses vehicles into pseudo-random positions. CS samples from t=10s to t=260s therefore represent a realistic geometric distribution — not just the artificial initial uniform spacing. 1000 packets (4 pkt/s × 250 s) provide statistically robust per-scenario CS means.

10.5 Relay Gap and Worst-Case CS

WITHOUT gap (would be a bug): relay@895m ──5m──▶ EVE@900m ◀──5m── relay@905m d_ie = 5m → C_ie = very high → CS ≈ 0 for both neighbours → protocol severely degraded WITH gap (correct design): relay@850m ─────50m────▶ EVE@900m ◀────50m───── relay@950m d_ie = 50m → C_ie = moderate → CS > 0 possible → realistic protocol comparison
